* ox-w3ctr --- org export backend for W3C TR CSS style

Based on Org-mode's ox-html.el and CSS of W3C Technical Report [[https://github.com/w3c/tr-design][tr-design]]'s base.css.

The current ox-w3ctr has not yet completed a full refactoring of the
ox-html code, though it’s already largely usable. I plan to release

When version 0.4 is released, the package should no longer introduce

version. In a sense, 0.4 will be the first official release.

** Install and Use

Please use Emacs 32.0.50 or above. Download this repo and add it to
=load-path=, or use =package-vc= like this:

#+begin_src text
M-x package-vs-install https://github.com/include-yy/ox-w3ctr RET
#+end_src

After installation and load, use =C-c C-e w o= to export a org buffer to
HTML file. See more information from docstrings and comments (at least
now).

The Node helper in =jstools/= is optional.  It renders math for the
=mathml-by-mathjax= and =svg-by-mathjax= modes and highlights code for
the =jstools= engine.  It needs =node= on =exec-path= and its packages:

#+begin_src sh
cd jstools && npm ci
#+end_src

*** Code highlighting

Source blocks are coloured by an engine named in
=org-w3ctr-fontify-method=:

- =engrave= (default): Emacs font-lock, through the language's major
  mode.
- =jstools=: Shiki (TextMate grammars, ~350 languages) in the Node
  helper.
- =plain= or nil: no colour.

A list tries engines in order, e.g. =(jstools engrave)=; =plain= always
ends it.  Override the method per file with =#+OPTIONS:
fontify:(jstools engrave)= and per block with a header argument:
=#+begin_src python :fontify nil=.

The output is =<span class="ef-SLUG">= runs; faces map to slugs through
=org-w3ctr-fontify-faces= (and =org-w3ctr-fontify-extra-faces=),
following =:inherit=.  The colours, light and dark, come from
=org-w3ctr-fontify-palette=; after changing it, run =M-x
org-w3ctr-fontify-update-stylesheet= to rewrite the generated block of
=assets/style.css=.  A block can recolour a slug locally with
=#+attr__: (style "--ef-k: red")=.

A language no engine knows, or an engine that fails, is warned about
once per export and the block exported as plain text (see
=org-w3ctr-fontify-unknown-language= and =org-w3ctr-fontify-on-error=).
=M-x org-w3ctr-show-fontify-report= lists, for the last export, which
engine took how many blocks, the languages no engine took, and the
faces that found no slug.  See [[file:doc/fontify.org][doc/fontify.org]] for the details: the
face table, colours, the Node engine, writing an engine of your own,
and how the pipeline works.

** Roadmap

*** TODO

- *Export entry fast path.*  Measured 2026-10: ~78% of corpus
  export time is =find-file-noselect='s per-document org-mode init,
  not the backend.  A raw-read path (=insert-file-contents= +
  =buffer-file-name= + =default-directory= + =org-export-as=, no
  =org-mode=) is byte-identical (=norm= across the 57 docs) and 4.4x
  faster (9.3s → 2.1s).  Apply it to the batch/corpus path (yynt's
  =yynt--do-export= already does this); per-document the saving is
  ~0.1s, so it only matters at batch scale.  Not the backend's job --
  an Org invocation concern.
- *Options tidy-up.*  The =:options-alist= is a grab-bag: a few
  entries are grouped, most are not.  Order every entry, consider
  replacing cumbersome string options with =*-function= ones.  Chart
  compatibility with ox-html for each option.  Known divergences to
  chart: =:html-link-use-abs-url= is unimplemented (FIXME in
  =org-w3ctr--link-path=); the legacy home/up bar emits our own =<nav
  id="navbar">= markup, deliberately not ox-html's =<div
  id="org-div-home-and-up">=.  =:html-home/up-format= keeps its
  ox-html keyword compatibility (=HTML_HOME/UP_FORMAT=, =newline=).
  =org-w3ctr-metadata-timestamp-format= drops ox-html's =%a= weekday
  abbreviation (deliberate).  =org-w3ctr-home/up-format=, a bare
  =format= string, is the natural =*-function= candidate.  Special
  blocks: with user attributes =org-w3ctr--special-block-builtin=
  replaces the type class instead of concatenating it as ox-html does
  (=class="user TYPE"=) — deliberate (explicit over implicit).
  Maximum flexibility is the rule for example and source blocks:
  =#+attr__:= / =#+attr_html:= replace the whole attribute list, so
  dropping =example= also drops the W3C box and its "Example N"
  counter; write =[example foo]= to keep both.  A captioned src block
  gets =class="example"= only when the author supplies no attributes
  (the class positions the self-link and hosts the caption box).

  low-value for W3C TR output).  Revisit later:
  - Line numbers and =retain-labels=.  Coderef links exist in a
    reduced form: =[[(label)]]= points at the defining block's id, the
    label text is stripped from the code (as ox-html does), and the

  - =:html-wrap-src-lines= and =:html-klipsify-src=.
  - Listing number in captions.
  - example-block fontification / line numbers.  The token list
    (=org-w3ctr--fontify-dispatch=) is where line numbers would be cut,
    without touching any engine.

  layers (=t--read-attr__=, =t--make-attr__=, =t--make-attr__id=,
  =t--make-attr__id*=, =t--make-attr_html=, =t--make-attribute-string=,
  =t--src-block-attrs=).  Two syntaxes coexist (Lisp s-exprs for
  =#+attr__=, plists for =#+attr_html=).  Candidates: a single
  intermediate representation or one canonical syntax.
- *SVG global font cache.*  =svg-by-mathjax= uses =fontCache: 'local'=.
  MathJax's =fontCache: 'global'= shares one =<defs>= per document
  (~1.9x smaller on a 100-formula sample).  Tried and reverted;
  revisit if SVG output is kept.
- *CSS cleanup in =assets/style.css=.*  Not urgent.
  - Dead rules: =.org-center= (never emitted).
- *Client-side highlighting.*  The server-side engines (=engrave=,
  =jstools=) are done (2026-10).  A =client= engine is designed but not
  built: it would emit =<code class="language-LANG">= unchanged and add
  highlight.js or Prism to =<head>= only when a document needs it.  It
  makes the page depend on browser JavaScript, so it waits for a
  concrete need.
- *Special-block custom elements: a component cookbook.*  The
  =:html-special-block-custom-elements= registry (=:template= for
  Declarative Shadow DOM, =:src= and =:script= for the =<head>=
  scripts) is the declared seam for authoring W3C components, and
  that is where the mechanism stops: no =org-special-block-extras=-
  style block DSL (a =defblock= macro that =read=s the block header
  and =eval=s raw HTML) is planned.  What belongs in the docs instead
  is a cookbook of correct component patterns for Org's always
  block-level =<p>= light content: style =:host= and reset
  =::slotted(p)= for inline components, wrap =<slot>= in a flow
  container for block components, route named slots with
  =#+attr_html: :slot NAME=, and choose =:src= vs =:script=.  Theme
  through CSS custom properties (=--w3c-*=), and, as optional sugar,
  map a block's =:parameters= (=#+begin_x-badge :variant warn=) onto
  element attributes.
- *Caption policy across blocks.*  =#+caption:= parses on nearly every
  block -- =example-block=, =src-block=, =quote-block=, =verse-block=,
  =center-block=, =special-block=, =table=, =fixed-width=,
  =latex-environment=, =export-block=, =drawer= -- but only four have
  a consumer today: the standalone-image paragraph
  (=<figure><figcaption>=), the table (=<caption>=), the captioned
  =src-block= (an unstyled =<span>= as the first child of its
  =.example= <div>), and the drawer (the caption reused as =<summary>=).
  Everything else drops the caption silently.
  W3C's base.css splits a caption in two: the *label and number* come
  from a CSS counter on the container class
  (=figcaption::before { content: "Figure " counter(figure) ". " }=,
  =.example::before= gives "Example N", and likewise
  =.issue::before= / =.note::before=), while the *text* is content the
  author supplies.  So the back-end picks the container/class and
  emits the text, and must not compute numbers in Elisp -- do not port
  ox-html's =org-export-get-ordinal= / "Listing N:" machinery.
  Decide a mapping {element -> container/class -> caption home},
  using W3C classes only (there is no =.quote= / =.verse= /
  =.center= counter):
  - figure (image paragraph) -> =<figure><figcaption>= (done).
  - table -> =<caption>= (done).
  - =example-block= / =src-block= -> =.example= <div>, caption in an
    unstyled =<span>= as the first child (done 2026-10-18).  A bare span
    because =.caption=/=figcaption= carry the figure counter; the span
    renders exactly like bare text but leaves a styling hook.  The
    =.example= class stays as before: always on =example-block=, added
    to a captioned =src-block=.
  - the rest (quote, verse, center, special, fixed-width,
    =latex-environment=, =export-block=) have no W3C home; do not
    invent one -- leave the caption dropped and say so.
  Pin the invariants while unifying: is the counter class applied only
  when captioned (=src-block='s rule) or always (=example-block='s)?
  And is the self-link anchor emitted on every captioned block or only
  =src-block=?  Decided 2026-10-17: a coderef target block gets an id
  but no ¶ self-link for now (the coderef link needs only the id); see
  the self-link TODO entry below for the deferred decision -- note that
  =.caption=/=figcaption= carry the figure counter, so an example
  caption cannot use them.

- *Self-links on literal blocks (deferred).*  Headlines and captioned
  src blocks emit =<a class="self-link">=; example blocks do not, and
  the coderef-target rule (2026-10-17) deliberately skips it.  The open
  question is the gate.  The block's id (a =#+name:= that becomes an id,
  or an explicit attribute id) is the only condition that is both
  explicit and free of invented syntax; reusing a begin-line switch
  (=-n=, =-k=) would make a coderef or line-number switch control
  presentation.  Placement is the =.example > a.self-link= slot (top
  right), as in a captioned src block; do not use =.marker=, because the
  automatic =.example::before= counter would duplicate the example
  number.

- *Arbitrary keyword support (consider, weigh carefully).*  Every
  backend drops an unknown =#+KEY:= line; =org-w3ctr-keyword= only
  handles H/HTML, E, D and TOC.  Emitting arbitrary keywords by
  default is the wrong default: keywords are metadata, not content
  (the corpus carries =#+TMP:= in 55 documents), and there is no W3C
  element or class for them.  The explicit hatches already exist:
  =#+HTML_HEAD:= / =#+HTML_HEAD_EXTRA:= for the head (including
  =<meta>=), =#+HTML:= and export blocks for raw body markup, =#+E:= /
  =#+D:= for computed output.  If a repeated need appears, the only
  shape that keeps "explicit over implicit" is an opt-in alist
  (key -> format string or function) consulted after the built-in
  branches, with a test for mapped/unmapped/built-in precedence.

- *Second check of the Lesser elements (after v0.2.19).*  The whole
  part was reviewed function by function, then edited by the coderef,
  caption, eval-gate and source-block passes and reordered (code
  references and example moved before the fontify pipeline).  Re-read it
  as one unit: docstrings, `declare' (ftype, important-return-value,
  pure), `t--pget'/`t--pput', `t-error', tests (coverage, section order,
  mutations), no stale REFINE/FIXME, and the backend transcoder /
  options / defcustom order matching the new source order.  Another
  model does the first read, then pi goes over its findings.  Shared
  gate: 320 ERT tests, strict compile, checkdoc, order-check (only the
  known Headline/CC disorder), test-map (293 functions, 20 uncovered),
  corpus (57 documents, 0 errors).

  Roadmap's dropped-features list; the only reason to keep it is ox-html
  compatibility, which this package does not promise.  If kept instead,
  record the decision like the Export blocks entry does.

*** Non-goals

Explicitly out of scope for now.

- *Dependency analysis.*  Charting how far ox-w3ctr leans on Org and
  mapping the internal =t-*= call graph.  Final global-optimization
  and cleanup task.
- *Cross-file link resolution (crossrefs).*  Resolving
  =[[file:other.org::*Heading]]= / =::#custom-id= to an anchor in the
  target document, with a project-scoped persistent cache.  Not now.
- *Drop the =ox-publish= dependency.*  Replace =org-publish-file-relative-name=,
  =org-publish-resolve-external-link=, and =org-publish-org-to= with
  local implementations.  Not now.
- *Option validation.*  Checking user-supplied export options and
  customization variables for well-formedness.  Options are trusted as
  given; the back-end verifies explicit markup only (attributes, block
  parameters), where malformed input fails loudly.  Not now.
- *Own export framework: streaming renderer / half-parser.*  Replace
  =org-export-data='s bottom-up string building and =org-element=
  parsing with a single-pass, head-to-tail renderer over a partial
  parser.  It means dropping the Org export contract -- filters,
  =:exported-data= memoization, string-returning transcoders,
  re-entrant call sites -- not optimising =org-export-data=.  The
  ceiling is small: the backend is only ~12% of export time (see next
  bullet).  Not now.
- *Backend micro-optimization.*  Don't over-optimize: the bottleneck
  is not the backend.  Measured 2026-10 over the 57-document corpus
  (time, not allocation): =find-file= + org-mode init ~78% (avoidable
  with raw read + =org-export-as=, no =find-file=),
  =org-export--annotate-info= keyword/macro preprocessing ~10%,
  parse-tree ~4%, backend transcode walk + transcoders +
  fontification ~12%.  ox-w3ctr is already faster than ox-html.

** Scratch

Notes about using pi (the coding agent) with this repo, kept here as
material for a future blog post.  Not part of the package.

*** Skills are code the agent runs

A skill is a directory with =SKILL.md= (frontmatter + instructions)
plus optional =scripts/=, =references/=, =assets/=.  pi advertises only
the name, description, and path at startup; the full instructions load
only when the task matches.  The description is therefore routing
information, not documentation.

- Write the description in three parts: what it does, when it applies
  (concrete triggers), and when it does not (negative routing).  A
  "Helps with X" description has no routing value.
- The =skill-maker= skill (in =.agents/skills/=) captures the pi spec
  and the create/review checklists.

*** Shell choice: Git Bash over MSYS2

pi runs each bash command in a fresh non-interactive shell, configured
by =shellPath= and =shellCommandPrefix= in =~/.pi/agent/settings.json=.

This checkout started on standalone MSYS2 (UCRT64) and moved to Git
Bash for one reason: Python wheels.  MSYS2's python is a mingw build
whose platform tag is =mingw_x86_64_ucrt_gnu=; PyPI ships =rpds-py=
only for =win_amd64= and =manylinux=, so pip fell back to compiling
Rust from source and hung.  Git Bash exposes the official Windows
Python (=win_amd64=), and the same =pip install= downloads a wheel and
finishes in seconds.

- Do not activate a venv through =shellCommandPrefix=: the prefix runs
  before every command, including the env-detect probe, which must see
  the *system* Python.  Keep the venv opt-in per task.
- Machine facts live in =.agents/env.md= (gitignored); project facts
  (the venv, its deps) live in =AGENTS.md= and =requirements.txt=.

*** env-detect: facts, fallbacks, and never overwriting a choice

The =env-detect= skill probes the machine and writes =.agents/env.md=.
The script decides the values, never the agent.  The probe chain for a
path is: an env override (=ORG_SOURCES=, =EMACS=) -> the value recorded
in =env.md= -> a derived default (the Org bundled with Emacs) -> FAIL.

When the recorded value is gone, the script emits =org_previous= and
falls back; the agent must report the change rather than silently
overwrite the user's choice.  Only a value the user never set falls
back automatically.
